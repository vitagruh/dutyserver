# Дежурная служба — учёт и распределение суточных дежурств

Небольшое веб-приложение для планирования суточных дежурств: ведёт календарь,
соблюдает обязательный отсыпной после дежурства, оформляет отгулы за дежурства
в выходные и праздники и проводит воспроизводимую жеребьёвку на спорный день.

Стек: Python 3.11+ (проверено на 3.15), FastAPI, SQLite, ванильный JS без сборки.
Оформление — конструктивизм в сдержанной подаче: плотная сетка, бумажный фон,
приглушённый красно-коричневый акцент, тонкие рамки и мягкие тени; есть
светлая и тёмная темы и переключатель языка интерфейса RU/EN.

## Быстрый запуск

```bash
# из каталога проекта
py -3.15 -m venv .venv
.venv/Scripts/python.exe -m pip install fastapi uvicorn

# демо-данные: 12 сотрудников, ~3 месяца графика, отпуска, отгулы
.venv/Scripts/python.exe seed_demo.py --force

# запуск
DUTY_DB=demo.db .venv/Scripts/python.exe run.py
# открыть http://127.0.0.1:8000 — откроется страница входа
```

Демо-данные создают учётные записи (`seed_demo.py` печатает их список):

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | `admin123` | администратор |
| `kovalev` | `lead123` | тимлид (привязан к сотруднику) |
| `sidorov`, `lebedev`, … | `duty123` | сотрудники |

Без демо-данных приложение стартует с пустой базой `duty.db`; первая учётная
запись администратора создаётся автоматически из `DUTY_ADMIN_USER` /
`DUTY_ADMIN_PASSWORD`. Если `DUTY_ADMIN_PASSWORD` не задан, генерируется
случайный пароль и один раз печатается в консоль при первом запуске. **Смените
пароль администратора сразу после первого входа.**
Путь к БД задаётся переменной окружения `DUTY_DB`, порт — `PORT`, хост — `HOST`.

## Правила

* **Отсыпной.** После дежурства следующий день недоступен этому сотруднику
  (`rest_days`, по умолчанию 1). Отсыпной нельзя «занять» дежурством.
* **Минимальный интервал.** Между двумя дежурствами сотрудника должно пройти
  не меньше `min_gap_days` дней (по умолчанию 2; всегда ≥ отсыпной + 1).
* **Защита следующего дня.** Дежурство не назначается, если на следующий день
  сотрудник уже стоит в графике: иначе отсыпной попадёт на чужое дежурство.
* **Отгул за выходные и праздники.** Каждое дежурство в выходной или
  праздничный день даёт право на один отгул. Дата выбирается сотрудником:
  только рабочий день, в пределах `comp_valid_days` (60) после дежурства,
  свободный от дежурств, отсыпных, отсутствий и других отгулов.
  Статусы: `ожидает` → `запланирован` → `использован`, либо `отказ`.
  Только «запланирован» и «использован» блокируют назначение дежурства.
* **Отсутствия.** Отпуск, болезнь, командировка исключают сотрудника из
  распределения на указанный период. Добавить отсутствие поверх дежурства
  нельзя — сначала снимите дежурство.
* **Праздники.** Государственные праздники РБ — 10 нерабочих дней, включая
  Радуницу (расчёт по православной пасхалии). Список подгружается автоматически
  при запуске для прошлого, текущего и следующего года; удалённые вручную даты
  повторно не добавляются. Кнопка «Заполнить праздники РБ» догружает или
  восстанавливает выбранный год. Праздничный день считается выходным.

## Доступ, роли и учётные записи

Вход — по логину и паролю (`/login`). Пароли хранятся как PBKDF2-SHA256
(600 000 итераций) с солью; минимальная длина пароля — 8 символов.
Сессия — подписанная HMAC-кука `duty_session` (HttpOnly, SameSite=Lax, 12 часов;
`Secure` при HTTPS). Выход из системы и смена пароля отзывают все выданные
ранее сессии этой учётной записи. Неудачные попытки входа ограничены:
10 ошибок за 5 минут на пару «IP + логин» → `429` с `Retry-After`.
Ответы приложения получают заголовки `Content-Security-Policy`,
`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` и
`Permissions-Policy`; при HTTPS добавляется `Strict-Transport-Security`.

| Роль | Что доступно |
|---|---|
| **Сотрудник** | личный кабинет `/me`: календарь, заявки, смена пароля; API `/api/me*` |
| **Тимлид** | график, заявки, отгулы, отсутствия, дни без покрытия, статистика, настройки |
| **Администратор** | всё то же + раздел «Аккаунты» и настройка уведомлений |

Учётные записи создаёт администратор в разделе «Аккаунты»: логин, пароль, роль,
привязка к сотруднику (одна запись на сотрудника), контакты для уведомлений.
Нельзя удалить собственную запись и оставить систему без активного администратора.
Сотрудник без привязанной карточки видит сообщение об ошибке — администратор
должен привязать его к записи в разделе «Сотрудники».

## Заявки сотрудников

Сотрудник входит в личный кабинет `/me` и отмечает дни в календаре. Заявка
уходит тимлиду на согласование, статус виден в кабинете; ожидающую заявку можно
отозвать.

Типы заявок:

* **«Не могу дежурить»** — жёсткое ограничение. После согласования сотрудник
  исключается из назначений на эти дни так же, как при отсутствии.
* **«Предпочитаю не дежурить»** — мягкая просьба. Назначение не запрещается,
  но автораспределение обходит такого сотрудника, если среди доступных есть
  альтернатива без роста нагрузки. В карточке кандидатов показывается
  предупреждение.

Заявки проходят согласование: `ожидает` → `согласована` / `отклонена`.
Согласовать заявку нельзя, если на эти дни у сотрудника уже стоит действующее
дежурство — сначала его нужно переназначить. Отозвать сотрудник может только
заявку в статусе «ожидает». О новой заявке и о решении тимлид и сотрудник
получают уведомления (если они настроены).

Ограничения против злоупотреблений:

* только текущая дата и вперёд, горизонт `request_horizon_days` (90 дней);
* не более `request_month_limit` дней в месяц на сотрудника (10, 0 — без лимита);
* нельзя подать перекрывающуюся заявку;
* заявки неактивного сотрудника не принимаются.

Списки и решения — в разделе «Заявки»; счётчик ожидающих заявок виден в шапке.
В календаре заявки показываются цветными чипами, в карточке дня — строкой
событий, а в таблице кандидатов — предупреждением. Жёсткие правила (отсыпной,
интервал, отгулы, отсутствия) остаются в силе независимо от заявок.

## Модель вероятности жеребьёвки

Нагрузка считается по фактическим и запланированным дежурствам:

```
L = будни × 1 + (выходные + праздники) × weekend_weight
```

`weekend_weight` по умолчанию 1.5 — выходное дежурство «дороже» буднего.
Отгул нагрузку не уменьшает: тяжесть выходного уже учтена коэффициентом.

Среди **отмеченных и доступных** кандидатов (жеребьёвка проходит только среди
них) вес равен:

```
w_i = (Lmax − L_i + 1) ^ power
P_i = w_i / Σ w
```

`power` (степень справедливости, по умолчанию 2) регулирует жёсткость:
1 — мягкий приоритет, 3–4 — сильный перекос в сторону менее загруженных.
Сотрудник с минимальной нагрузкой получает максимальный шанс, но выбор
остаётся случайным. При равной нагрузке шансы равны.

Пример: нагрузки 6.5, 8.0, 9.5. Lmax = 9.5, power = 2:
веса 16, 4, 1 → вероятности 76%, 19%, 5%.

Розыгрыш использует `random.Random(seed)`. Seed, случайное число `roll`,
таблица весов и вероятностей всех кандидатов, победитель и SHA-256-печать
сохраняются в таблице `draws`, поэтому результат можно воспроизвести и
проверить независимо. В интерфейсе вероятности пересчитываются сразу
при снятии/установке галочки — по той же формуле.

**Автораспределение** заполняет только пустые дни: каждый раз выбирается
сотрудник с минимальной взвешенной нагрузкой, при равенстве — случайно
(seed сохраняется в примечании к дежурству). Уже занятые дни не трогает,
поэтому повторный запуск безопасен.

### Пруф жеребьёвки

Каждый розыгрыш получает ссылку **«Пруф»** (`/proof/{draw_id}`): страница
с печатью, seed, `roll`, таблицей весов и вероятностей и автоматической
проверкой. API `GET /api/proof/{draw_id}` отдаёт канонический пакет (`seed`,
`roll`, кандидаты, веса, победитель), SHA-256-хеш и результат проверки.

Как проверяется:

1. Пакет сериализуется канонически (JSON, `sort_keys`, компактные
   разделители) и хешируется SHA-256 — хеш должен совпасть с сохранённым.
2. Все веса положительны, вероятности в сумме дают 1.
3. Независимый пересчёт: `threshold = roll × Σweights`, затем ищется первый
   интервал накопленных весов, накрывающий порог, — победитель должен
   совпасть с записанным.

Страница показывает «ПОДТВЕРЖДЕНО» только если сошлись все проверки;
для старых розыгрышей без пруфа выводится пометка «архив». Журнал
«Аудит жеребьёвок» на вкладке статистики содержит дату, режим, победителя,
seed, короткий хеш и статус; бейдж ведёт на страницу пруфа. Пруф доступен
любой вошедшей учётной записи.

### Визуальная рулетка

Кнопка **«Рулетка»** в шапке графика (или в карточке свободного дня) открывает
выбор даты и колесо с сотрудниками. В режиме по умолчанию доступны только
сотрудники без отпуска, отсыпного, нарушенного интервала, отгула и
согласованной заявки. Переключатель режима:

* **Дежурства за месяц** — вес `(Mmax − M + 1)^power`, где M — число дежурств
  сотрудника в месяце целевой даты. Кто меньше дежурил в этом месяце, получает
  больший сектор и шанс. Общая нагрузка и тяжесть выходных здесь не учитываются.
* **Равные шансы** — дежурства не учитываются вовсе: у всех вес 1, вероятность
  `1 / N`.

Флажок **«Не блокировать интервал, отгул и заявки — исключать только отпуск и
отсыпной»** оставляет жёсткими только отсутствия и отсыпной день. Остальные
ограничения превращаются в отклонения: такие сотрудники участвуют в колесе,
отклонения показываются в списке участников, в результате и в примечании к
дежурству.

Если на дату уже назначено плановое дежурство, рулетка предлагает переиграть
день: после подтверждения старое дежурство отменяется, а новое назначается тем
же розыгрышем. Переигровка запрещена, если за старое дежурство уже оформлен или
использован отгул, и для дежурств со статусом «выполнено»/«неявка».

Размер сектора равен вероятности. Сервер фиксирует результат (`seed`, таблица
вероятностей в `draws`), назначает дежурство, а колесо анимированно
останавливается на победителе; режим и отклонения пишутся в примечание к
дежурству. Результат рулетки, как и обычной жеребьёвки, получает пруф и строку
в журнале «Аудит жеребьёвок».

## Дни без доступных сотрудников

На горизонте планирования система ищет дни, на которые не назначено дежурство
и где **ни один** активный сотрудник не может дежурить (отпуск, больничный,
отсыпной, интервал, отгул, согласованное «не могу»). Такие дни попадают в
раздел **«Требуют решения»** с разбивкой причин по каждому сотруднику, списком
отсутствующих и ожидающих согласования заявок.

Для каждого такого дня система отдельно считает **пул для решения**: отпуска,
отсыпной, интервалы и согласованные заявки не блокируют кандидата, а
показываются как отступления. По этому пулу считается тот же коэффициент, что и
при жеребьёвке, — вес `(Lmax − L + 1)^power` и вероятность `вес / Σ весов`.
Кандидаты сортируются по вероятности; в карточке назначения сразу видно
коэффициент, шанс и все отступления выбранного сотрудника. Нагрузка при этом
считается по фактической истории, поэтому менее загруженные получают больший
коэффициент.

Тимлид может:

* **Назначить дежурного поверх правил** — обязательна причина (не короче
  5 символов); назначение, причина и автор пишутся в журнал
  «Назначения поверх правил» (`coverage_overrides`), сотрудник получает
  уведомление; предупреждения о нарушенных правилах показываются сразу;
* **Снять день с контроля** — с комментарием; день исчезает из списка, но
  остаётся в журнале и может быть возвращён кнопкой «Вернуть в контроль».

При включённых уведомлениях тимлиды получают одно письмо/сообщение о появившихся
днях без покрытия; повторно один и тот же день не уведомляется
(`coverage_alerts`), а при закрытии дня запись об алерте удаляется.

## Уведомления email и Rocket.Chat

Настройки → «Уведомления» (только администратор): общий выключатель, флаги
событий (новая заявка, решение по заявке, дни без покрытия), SMTP (сервер, порт,
пользователь, пароль, адрес отправителя, STARTTLS) и webhook Rocket.Chat,
адрес системы для ссылок в письмах.

Сообщения не отправляются синхронно с запросом: они ставятся в очередь
`notification_outbox`, фоновый поток доставляет их и фиксирует статус
`в очереди` / `отправлено` / `ошибка` с текстом ошибки. Кнопки «Тест email» и
«Тест Rocket.Chat» отправляют сообщение на контакты текущей учётной записи,
«Повторить ошибки» возвращает неудачные сообщения в очередь. Журнал отправки
виден в том же разделе. Пароль SMTP в API не возвращается — только признак
`smtp_password_set`.

## Интерфейс

* **График** — календарь на месяц: дежурные, отсыпные, отгулы, отсутствия,
  заявки, праздники, KPI и журнал розыгрышей. Клик по дню открывает карточку:
  смена статуса дежурства, оформление отгула, таблица кандидатов
  с нагрузкой, вероятностями и предупреждениями о заявках, назначение вручную,
  жеребьёвка или **визуальная рулетка** с режимами «равные шансы» и
  «дежурства за месяц».
* **Сотрудники** — состав, заметки (смены), контакты (email, Rocket.Chat),
  деактивация с сохранением истории.
* **Заявки** — заявки сотрудников с фильтрами, согласованием и отклонением.
* **Требуют решения** — дни без доступных сотрудников: причины, кандидаты
  с коэффициентом, назначение поверх правил, снятие с контроля и журнал
  решений (счётчик в шапке).
* **Отгулы** — все права на отгул с фильтрами и сроками выбора.
* **Отсутствия** — отпуска, больничные, командировки.
* **Статистика** — дашборды на одном экране:
  * шесть KPI: дежурств за период, средняя нагрузка, покрытие горизонта,
    выходных закрыто, неявки, отгулы;
  * **баланс нагрузки** — отклонение взвешенной нагрузки каждого сотрудника
    от среднего (недогружен / перегружен), чтобы видеть перекос сразу;
  * **матрица «сотрудник × месяц»** — тепловая карта числа дежурств
    по месяцам периода;
  * **горизонт покрытия** — закрытые, открытые и снятые с контроля дни,
    прогресс-полоса и список ближайших проблемных дат;
  * **доля выходных** — кто чаще дежурит в нерабочие дни, шкала 0–100 %;
  * **таблица «сотрудник × день недели»** с количеством дежурств в ячейках
    и строкой итогов;
  * детальная таблица: всего/будни/выходные, взвешенная нагрузка и отклонение,
    план/выполнено/неявки, отгулы, последнее и следующее дежурство;
  * **аудит жеребьёвок** с ссылкой на пруф и формулой нагрузки.
* **Аккаунты** — учётные записи, роли, привязка к сотрудникам, пароли.
* **Настройки** — правила, веса, лимиты заявок, справочник праздников,
  уведомления и журнал отправки (уведомления — только администратор).

### Темы

Переключатель темы в шапке (на странице входа — в правом верхнем углу)
подписан целевой темой: в светлой показывает «Тёмная», в тёмной — «Светлая». Выбор хранится в
`localStorage` (`duty-theme`); без явного выбора используется системная
настройка `prefers-color-scheme`. Тема применяется до отрисовки страницы,
поэтому переключение не даёт вспышки; `color-scheme` согласует с ней
нативные контролы. Для печати всегда используется светлая палитра.

### Язык интерфейса (RU/EN)

Кнопка **EN / RU** рядом с переключателем темы (на странице входа — отдельной
кнопкой под ним) переводит интерфейс целиком: SPA тимлида и администратора,
личный кабинет сотрудника, страницы входа и пруфа, включая нативные диалоги
`confirm`/`alert`/`prompt` и тексты ошибок сервера в тостах. Выбор хранится
в `localStorage` (`duty-lang`), по умолчанию интерфейс русский; `<html lang>`
обновляется, так что скринридеры и автоперевод браузера видят правильный язык.

Перевод — слой поверх разметки (`app/static/i18n.js`): точный словарь
RU→EN, правила для динамических фраз (даты, месяцы, числительные, счётчики,
заголовки с именами) и `MutationObserver`, который переводит и контент,
добавленный после загрузки. Исходный русский текст запоминается, поэтому
переключение туда-обратно не портит разметку.

Что остаётся как есть: ФИО, должности, заметки и причины заявок, введённые
пользователями; Excel-выгрузка и CSV; письма и сообщения Rocket.Chat;
канонический JSON пакета жеребьёвки. Это данные и внешние артефакты, а не
элементы интерфейса — их перевод исказил бы отчётность.


Экспорт CSV (UTF-8 BOM, разделитель `;`) открывается в Excel с русской локалью.
Кнопка **«Excel для печати»** на странице графика выгружает XLSX из двух листов:

* **«ФИО-Дата»** — матрица: строки — сотрудники, столбцы — даты периода,
  в пересечении `Д` — дежурство. Столбцы выходных залиты розовым, праздников —
  жёлтым; в конце — «Всего» и «Вых.». Первая колонка и шапка закреплены,
  при печати повторяются на каждой странице;
* **«Список»** — детальный график по датам: дежурный, статус, отгул,
  примечание.

Оформление печати: A4 landscape, колонтитулы, строки для подписей. Генератор
XLSX написан на стандартной библиотеке (`zipfile` + OOXML), внешние
зависимости не нужны.

## Ограничения

Одна должностная группа (подразделение). Авторизация локальная (логин/пароль,
без внешнего SSO и LDAP); сессии живут 12 часов. Нет ограничения попыток входа —
при публикации в интернет ставьте reverse-proxy с rate-limit и HTTPS
(кука сессии при этом должна идти только по TLS). Уведомления отправляются
фоновым потоком без повторов по расписанию: неудачные сообщения остаются
в журнале и повторяются кнопкой. SQLite достаточно для сотен сотрудников
и нескольких лет графика; при необходимости легко заменить на PostgreSQL.
